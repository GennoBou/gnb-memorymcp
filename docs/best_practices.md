# GNB MemoryMCP 活用ベストプラクティス

本ドキュメントでは、個人向けの高速・大容量（Turso 無料枠 5GB / SQLite FTS5）という特性を活かし、LLM に GNB MemoryMCP を最も効果的に活用させるための「起動条件」「起動ワード」、および「雑多記憶・非同期整理（クレンジング）」の設計・運用ベストプラクティスを提案します。

---

## 1. 基本コンセプト：「雑多記憶・非同期整理」パターン

会話の最中に LLM が記憶を「綺麗に分類・構造化」しようとすると、以下のデメリットが生じます。
- **レスポンスの遅延**: 構造化の検討や複数のツール呼び出しにより、ユーザーとの対話のテンポが悪くなる。
- **コンテキストの消費**: 記憶の構造化ルールを LLM に意識させ続けるため、システムプロンプトやトークンが余分に消費される。

### 提案：書き込みは「雑」に行い、整理は「後からまとめて」行う
Turso の 5GB という容量は、個人用のテキスト記憶であれば実質的にほぼ無限（数百万件規模）です。また SQLite/FTS5 による全文検索は非常に高速なため、**「重複や雑多なデータが多少あっても、想起（検索）の速度や精度には影響しない」**という強みがあります。

- **対話中**: LLM はユーザーの重要な事実や決定事項を検知したら、体裁を整えず、会話の文脈をそのまま `memory_create` で「雑に」保存します。
- **アイドル時 / 明示的な指示時**: ユーザーからの「記憶を整理して」という指示や、定期的なクレンジング指示をトリガーに、LLM が `memory_status` や `memory_consolidate` を使用して、重複・矛盾する記憶をバックグラウンドでマージ・整理します。

---

## 2. LLM に自動で MCP を使わせるための設計（起動条件・起動ワード）

MCP サーバーは登録するだけでツールが公開されますが、LLM が「いつ呼べばいいか」を自律的に判断できるようにするには、**「ツールの Description の最適化（サーバー側）」** と **「システムプロンプトの記述（クライアント側）」** の両面からのアプローチが必要です。

### A. ツールの Description（説明文）のチューニング（サーバー側）
LLM は MCP ツールの Description を頼りにツールの実行判定を行います。Description に「どのような場面で呼び出すべきか」を明記しておくことで、自動実行率が大幅に向上します。

以下は、`pkg/mcp/handler.go` で定義するツールの説明文の推奨チューニング例です。

| ツール名 | チューニング後の Description（推奨） |
| :--- | :--- |
| `memory_create` | **新規記憶を「雑に」保存します。** 会話中、ユーザーに関する新しい事実、好み、プロジェクトの決定事項、技術的な教訓（バグ解決策など）が判明した際、会話のテンポを崩さないよう、体裁を整えず文脈のまま素早く記録するために使用してください。 |
| `memory_search` | **過去の記憶を想起・検索します。** 会話の開始時や、ユーザーが「前に話した件」「いつもの設定」などの過去のコンテキストに言及した際、または現在の課題に関連する過去の知見がないかを確認するために、まずこのツールで検索を実行してください。 |

### B. クライアント側のシステムプロンプト（カスタム指示）
各種 LLM クライアント（Antigravity, Claude Desktop, Claude Code 等）のシステムプロンプトやカスタムインストラクションに、以下の指示を組み込みます。

```markdown
# 外部記憶（GNB MemoryMCP）の利用ルール

あなたには外部記憶にアクセスするためのツール群（`memory_*`）が提供されています。
ユーザーとの対話の質を向上させるため、以下のガイドラインに従って自発的に記憶の参照・保存を行ってください。

## 1. 記憶の想起（検索：`memory_search`）のトリガー条件
以下の状況では、ユーザーから明示的な指示がなくても、自発的に `memory_search` を呼び出して過去の情報を確認してください。
- **セッション開始時**: ユーザーと新しい会話を始めた直後、前回の状態や進行中のタスクを確認するため（例: クエリ `「直近のタスク」「プロジェクトの基本情報」` 等で検索）。
- **曖昧な指示の受け取り時**: ユーザーが「前言ってたやつ」「いつもの設定で」など、過去の文脈を前提とした発言をした場合。
- **技術的トラブルの発生時**: エラーやバグが発生し、過去に同様の解決事例がないか確認したい場合。

## 2. 記憶の保存（作成：`memory_create`）のトリガー条件
会話の中で以下の情報が明らかになった場合、会話の流れを阻害しない程度に、素早く `memory_create` を呼び出して記憶してください。
- **ユーザーの個人的な好み・属性**（例: 「エディタはダークモードが好き」「Goのプロジェクトが多い」）
- **プロジェクトのルール・設計判断**（例: 「このリポジトリでは外部ライブラリを最小限にする」「インフラはAWS lambdaを使う」）
- **トラブルシューティングの教訓**（例: 「~~のエラーは~~が原因だった。~~で解決した」）
- **記憶する際の注意**: 綺麗に構造化しようと時間をかける必要はありません。文脈が伝わる内容であれば、雑多なメモ書きのままで構いません。

## 3. 明示的な起動ワード（ユーザー指示へのフォールバック）
システムが自動的に判断できない場合のため、以下の起動ワードを認識した場合は、指定されたツールを即座に実行してください。
- 「**覚えておいて**」「**記憶して**」「**メモして**」: 直前の重要な内容を `memory_create` で保存する。
- 「**思い出して**」「**前話したっけ？**」「**過去の履歴から探して**」: 関連するキーワードで `memory_search` を実行する。
- 「**記憶を整理して**」「**クレンジングして**」: 記憶の整理セッション（クレンジング）を開始する。
```

## 3. 「雑多記憶」のクレンジングプロセスの標準化

「雑に記憶する」運用のツケを払うために、LLM 自身に定期的に記憶を整理させるプロセスを定義します。

### クレンジングの流れ（LLM が自律的に実行）

ユーザーから「記憶を整理して」という指示を受けるか、`memory_status` の結果 `Requires cleanup: true` になっていることを検知した場合、LLM は以下のステップを順番に実行します。

1. **`memory_status`** を呼び出し、現在の記憶数とクレンジングが必要かを確認する。
2. **`memory_consolidate`** を呼び出し、重複または矛盾している可能性のある記憶グループ（最大3グループ程度）を取得する。
3. 返された各グループについて、以下を実行する：
   - **比較と評価**: どの記憶が最新で、最も正確か（または情報量が多いか）を判断する。
   - **統合 (Update)**: 最も適した記憶IDの `content` に、グループ内のすべての有用な情報をマージして更新する。タグやメタデータも必要に応じて補完する。
   - **削除 (Delete)**: 統合によって不要になった、グループ内の他の記憶IDをすべて削除する。
4. `memory_consolidate` で候補が返ってこなくなるまで（またはクリーンになるまで）繰り返す。
5. 最後に **`memory_cleanup_complete`** を呼び出して、クレンジングが完了したことをシステムに記録する。

## 4. 各種 LLM / クライアントでの導入イメージ

### Claude Desktop
`claude_desktop_config.json` に GNB MemoryMCP を登録する際、Claude 自体にシステムプロンプトを直接流し込む公式な方法は現在ありませんが、**各プロジェクトの `README.md` や、プロジェクト開始時にユーザーからカスタムシステムプロンプト（前述の「外部記憶の利用ルール」）を1度コピペして与える**ことで、非常に高い精度で動作します。

### Antigravity (Gemini) / Claude Code / Cline
これら開発者向けの高度な AI エージェントでは、設定ファイルやシステムプロンプトのカスタマイズ機能（例: `.clinerules` や `settings.json` のプロンプト設定、または Serena MCP のような `initial_instructions`）が提供されています。
これらに前述の「外部記憶（GNB MemoryMCP）の利用ルール」を定義しておくことで、**エージェントがエディタ操作やコマンド実行の合間に、完全に自律して記憶の作成と検索を行う**ようになります。
